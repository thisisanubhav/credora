# M6 notification policy

Workflow C consumes only the committed `matching.completed.v1` outbox event for a successfully matched batch. It groups `matches.status='potential'` by batch-scoped user and sends at most one message per user per batch. It excludes withdrawn matches, review-required/ineligible decisions (which are not stored as matches), retired or unverified product versions, and any match already linked in `notification_matches`. A user with no new matches receives nothing. A match remains tied to the immutable product version evaluated in M5. The message says, verbatim, **“These are potential matches, not guaranteed loan approvals.”** Neither salary nor credit score nor CSV email appears in content or logs.

## Recipient isolation and content

Only `NOTIFICATION_MODE=test` exists. `NOTIFICATION_TEST_EMAIL` is the sole delivery destination; the CSV address is never read by the notification query. For a Gmail/Googlemail test inbox, the service deterministically derives `+loan-<first eight user UUID characters>` aliases; another domain uses the exact configured test address. Synthetic batches and products never enable production recipients. A local run defaults to `NOTIFICATION_TRANSPORT=mock`, `NOTIFICATION_SES_ENABLED=0`, and an `.invalid` placeholder address; it does **not** send email. SES requires an explicit `ses` transport, enable switch, non-placeholder sender/test identities, and a verified AWS SES credential configured in n8n. The internal preflight checks the mode, route, destination, synthetic batch, match membership, and state in a transaction before the SES node can run. The mock endpoint independently checks the destination and never connects to SES.

Text and escaped HTML renderings are produced from verified product-version name, institution, published rate text when available, and stored HTTPS source URL. Unknown interest rates are labelled unpublished. Synthetic fixtures carry an unmistakable “NOT A REAL LENDER OFFER” label and link only to the reserved fixture URL. The installed n8n 2.43.5 AWS SES `email.send` node supports either an HTML body or text body, **not a multipart alternative**; Workflow C selects UTF-8 HTML for a real send while retaining the plain-text rendering in the service contract. A multipart requirement for production would need a reviewed SES template containing both parts or another node/API design. This limitation must not be represented as dual-part delivery in a video.

## Idempotency and recovery

- `notification_logs.idempotency_key = SHA-256(batch UUID, user UUID, template version)` ensures one reservation for the user/batch. Unique `notification_matches.match_id` prevents a match being reserved twice. Row locks serialize concurrent workflow attempts. A notification run has a unique parent outbox event and records a heartbeat/cursor.
- States: `reserved` (safe to resume), `sending` (attempt begun; provider outcome may be unknown), `sent` (SES accepted and returned a message ID, **not inbox delivery**), `mocked` (local fake acceptance, no email), `failed` (known local/mock failure), `ambiguous` (SES error/timeout, missing message ID, or interrupted sending). The existing `attempt_count`, timestamps, SES message ID, and sanitized error code are retained. The default SES attempt limit is one; ambiguous outcomes require manual reconciliation, never automatic resend.
- The dispatcher uses a 90-second fenced claim, `FOR UPDATE SKIP LOCKED`, HMAC SHA-256, a five-minute timestamp window, up to 12 bounded backoff attempts, and requeues an acknowledged event if its workflow heartbeat stalls. HTTP 202 counts only after the receiver commits a notification execution. A webhook replay of the same completed event returns the existing run. A crash after SES accepts but before `sent` is committed leaves `sending`; recovery marks it `ambiguous` and advances without retrying. This avoids blind duplicates, but cannot guarantee exactly-once delivery.
- A Workflow C failure never rolls back Workflow B matches. A failed/ambiguous notification does not create a new matching decision. Operators must inspect the SES message ID and provider/inbox evidence before any manual recovery. No SES result or inbox receipt is claimed in the local demonstration.

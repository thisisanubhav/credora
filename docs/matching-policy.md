# M5 eligibility policy

An `ELIGIBLE_POTENTIAL` decision means only that every *represented, source-supported* rule passed for the supplied data. It is not approval or a lender offer. `INELIGIBLE` means at least one hard rule failed, even if another field is unknown. `INSUFFICIENT_DATA` means a required applicant field (including income currency) is unavailable. `REVIEW_REQUIRED` means the product itself has an unverified, ambiguous, or unknown decision-critical condition. Only `ELIGIBLE_POTENTIAL` becomes a `matches.status='potential'` row; other outcomes contribute aggregate execution metrics rather than creating potentially hundreds of thousands of negative rows.

The actual [SBI](https://sbi.bank.in/web/personal-banking/loans/personal-loans/sbi-personal-loan) and [Axis Bank](https://www.axis.bank.in/loans/personal-loan) records discovered in M4 are `review_required`. Workflow B's SQL gate requires current `verified` products, so neither can produce an automatic match. The assignment CSV contains no currency; an income rule stated in INR cannot be compared to an unlabelled amount. `Business` maps to `other`, which cannot automatically satisfy a named employment restriction.

`eligibility_rules` is schema version 1. The evaluator is `deterministic-v1`; it uses `Decimal`, strict typed facts, `all`/`any` semantics, hard-failure precedence, explicit reasons, and source-supported evidence references. Its decision hash covers normalized user facts, the immutable product version and rule document, and the evaluator version. Successful rows retain user and product-version FKs, execution FK, timestamp, method, passed reason codes, and input hash. The batch is reachable through `users.upload_batch_id`. A rerun uses the `(user_id, product_id)` unique constraint and does not overwrite an old decision. If a source changes, Workflow A creates a new product version instead.

SQL prefiltering checks known hard bounds for age, credit score, income and currency, employment, product current/verified/retired state, and synthetic isolation. A SQL `NULL` projection is **not** a passing eligibility rule: the deterministic evaluator still checks the structured rule document and knowledge states. A missing user currency excludes a product with an income threshold. A missing or unknown product rule cannot turn into a match. The service never loads user email for matching.

Two fixtures at `https://synthetic.invalid` have `source_type='synthetic'` and names prefixed `SYNTHETIC DEMO`. The address is a reserved non-source placeholder and is never crawled. An upload must explicitly set `demo_mode=true`, which the local API accepts only when ignored `.env` has `ALLOW_SYNTHETIC_DEMO=1`. Ordinary batches cannot see those products even if they are marked verified for fixture evaluation. This demo flag must be disabled in any shared or production environment. The profile-only fixture explicitly has income/currency `NOT_APPLICABLE`, allowing a positive decision from the currency-unspecified assignment CSV without inventing a currency. The separate INR fixture tests income and currency boundaries but cannot match that CSV automatically.

Gemini is advisory only for a pair already classified `REVIEW_REQUIRED` after hard rules pass. The verifier sends no email, external user ID, or CSV body, permits at most five calls per run, validates structured output, and does not promote an unresolved pair to eligible. With no key, it returns `unavailable` and makes zero calls. The configured stable model is [Gemini 3.8 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash). No live Gemini evaluation was performed in M5.

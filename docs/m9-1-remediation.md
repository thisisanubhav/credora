## P1 — n8n webhook execution records stayed `running`

**Reproduction:** before the fix, send correctly HMAC-signed replay events to the published B/C webhooks. Both returned 202 with existing app run IDs, while n8n executions 144/145 had `status=running`, null `stoppedAt`, and empty saved `runData`. Earlier IDs 137–143 showed the same condition. The helper's committed work was real, but n8n's own terminal state was not. n8n pruned those old incomplete rows after restart; they were never manually rewritten.

**Root cause isolated by controlled change:** B/C exports explicitly set `saveDataSuccessExecution=none` (and C also `saveDataErrorExecution=none`). On this installed n8n 2.43.5 webhook path, those settings left execution bookkeeping nonterminal. Changing only the settings to `all`, reimporting/publishing/restarting, and replaying the same events produced n8n 146/147 `success` with stop times and saved node data. A new full batch then reached every B/C stage, including both final summary nodes. This is an observed version-specific behavior; it is not a general claim about all n8n releases. No execution status row was edited.

**Regression:** `scripts/notification_e2e.py` now cross-checks n8n's database for a terminal successful execution containing the exact app run UUID and final summary node. `tests/discovery/test_discovery.py` asserts B/C retain success/error execution data and all internal HTTP nodes are signed. Real n8n B/C 156/157 and browser B/C 159/160 were `success`, with stop times; replay 161 was also terminal. Deliberately invalid webhook events produced terminal `error` rows 162/163. The webhook's generic 500 on invalid signatures is safe but less precise than a 401; the private helper itself returns 401.

**Privacy tradeoff:** successful n8n run data now persists for evidence and troubleshooting. Compose bounds it to 72 hours/1,000 executions. The local n8n database/volume and editor are private to this machine; do not copy execution data into committed evidence or make the editor public.

## P1 — private helper trusted network membership alone

**Reproduction:** M9 found direct POSTs to discovery/matching/notification helper stages needed no authentication from another Compose peer. **Fix:** every non-health helper request now carries an HMAC-SHA256 over key ID, UTC Unix timestamp, UUID nonce, method, path and canonical JSON body. A FastAPI middleware verifies the signature in constant time, rejects timestamps outside five minutes, and atomically reserves `(key_id, nonce)` in a PostgreSQL table. Duplicate nonces are rejected; expired rows are amortized-pruned. The active key and optional previous key support rotation. The runtime DB role has only required nonce-table DML. Key values remain in ignored `.env` and container environment, never workflow JSON; n8n Code signer nodes precede all 21 private HTTP stages and preserve explicit workflow orchestration.

**Verification:** an unsigned request from the n8n container returned helper HTTP 401. The real scheduled A run, real B/C browser run and signed duplicate replay passed after authentication. Unit/integration tests cover missing/incorrect signatures, route binding, timestamp expiry, replay and previous-key acceptance. The local n8n 2.43.5 JS task runner required `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` and `NODE_FUNCTION_ALLOW_BUILTIN=crypto` for signer nodes; this is acceptable only for a single-owner loopback editor. A shared/cloud n8n deployment should move the signer into an isolated task runner or encrypted credential-backed node so unrelated workflow editors cannot read process environment variables. That remains a production security blocker, not a hidden credential claim.

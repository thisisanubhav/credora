# Workflow C — n8n user notifications

Import `workflows/notifications.json` with `make notification-import`. The workflow is importable in n8n 2.43.5 and contains the actual `n8n-nodes-base.awsSes` node, with no embedded credentials. Publish it in n8n and restart n8n before the production webhook at `/webhook/loan-notifications` accepts events. The same local outbox dispatcher from M5 now routes `matching.completed.v1` to `NOTIFICATION_WEBHOOK_URL` and `upload_batch.ready.v1` to Workflow B. Run `make matching-dispatch` until both events have been dispatched, or run the documented E2E command. Continuous dispatch uses `python -m services.eligibility.dispatcher --watch`; no background daemon is installed by this milestone.

Node order: Signed Notification Webhook → Authenticate and Durably Accept Event → duplicate branch / 202 ACK → Fetch and Reserve Next User Group → completion or skip branch → Group Verified Matches and Compose Text + HTML → Enforce Test Recipient and Begin Attempt → mock/SES branch → Record Result → next user → Execution Summary. Database transactions live in bounded internal helper endpoints; n8n owns the loop, branching, SES invocation, and stage visibility. Duplicate events do not start concurrent sends. The ACK follows committed execution acceptance, not delivery completion.

## Optional controlled SES configuration (not executed in M6)

SES requires a verified sender identity in the chosen AWS Region, and sandbox accounts generally require a verified test recipient as well ([AWS sandbox guide](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html)). Create a least-privilege n8n AWS credential with only `ses:SendEmail` for the verified identity/region; store it in the n8n credential store, never in JSON or `.env`. Select that credential on the AWS SES node and configure its region there. Set ignored `.env` values `NOTIFICATION_TRANSPORT=ses`, `NOTIFICATION_SES_ENABLED=1`, `NOTIFICATION_TEST_EMAIL=<controlled verified inbox>`, `NOTIFICATION_FROM_EMAIL=<verified sender>`. Recreate the internal helper with `make up`. **Do not switch modes using sample CSV addresses.** Even when SES returns a `MessageId`, that means request acceptance, not actual inbox delivery ([SES API](https://docs.aws.amazon.com/ses/latest/APIReference/API_SendEmail.html)). For the assignment video, check the controlled inbox independently and show a sanitized received email; no such evidence is available from the local mock run.

SES can reject, time out, or accept before the result callback commits. The workflow's SES node continues to the result-recording stage on a node error; absent message IDs become `ambiguous`. A process crash leaves `sending`, which the recovery path also marks `ambiguous`. Automatic retry of those messages is prohibited. The current n8n SES node sends UTF-8 HTML only; plain text is generated and tested but not carried as a multipart alternative. This is a known limitation to resolve if dual-part MIME delivery is required in production.

The helper uses `NOTIFICATION_TEST_EMAIL` **exactly** in SES mode (no Gmail plus-alias rewriting), so the verified recipient must be the configured address itself. Do not use a CSV address. Keep the node's `To Addresses` bound to preflight `recipient` and its `From Email` to preflight `sender`.

The earlier ambiguous SES attempt remains untouched. The new gate authorizes a **new** synthetic batch and exactly one logical notification, identified by the pair `NOTIFICATION_SES_AUTHORIZED_BATCH_ID` and `NOTIFICATION_SES_AUTHORIZED_IDEMPOTENCY_KEY`. The key is `idempotency_key(batch_id, user_id)` from `services.notifications.content`; it identifies the batch/user/template reservation, not the CSV email. The preflight additionally requires one persisted user, one potential match to one verified synthetic product, a demo batch, a reserved SES notification, and an exact controlled recipient. It holds a PostgreSQL advisory transaction lock and counts prior SES attempts **in that batch**; an ambiguous attempt consumes that batch's allowance. Another notification, batch, or user cannot use the configured authorization, and the previous ambiguous record cannot be retried. The cap is test-specific, not a production sending policy.
